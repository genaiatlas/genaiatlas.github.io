    Introduction & Problem Formulation

    Business Context and Motivation

    Music streaming platforms like Spotify face a fundamental challenge: how to keep users engaged by recommending the "best" next song from millions of available tracks. The success of these platforms directly correlates with user engagement time, making recommendation systems critical business assets rather than just technical features.

    Core Problem Statement

    Objective: Build a recommendation system to propose the top 10 songs for a user based on their likelihood of listening to those songs.

    Key Questions:

    • What songs has a user historically consumed?

    • Which songs and artists show the highest user preference patterns?

    • How can we predict user preferences for unheard songs?

    Dataset Overview

    The analysis uses the Taste Profile Subset from The Echo Nest's Million Song Dataset, consisting of:

    song_data.csv:

    • song_id: Unique identifier for each song

    • title: Song title

    • release: Album name

    • artist_name: Artist name

    • year: Release year

    count_data.csv:

    • user_id: Unique user identifier

    • song_id: Song identifier (links to song_data)

    • play_count: Number of times user played the song

    Methodological Framework

    This tutorial implements six distinct recommendation approaches:

    1. Popularity-Based: Rank songs by average play counts (cold start solution)

    2. User-User Collaborative Filtering: Find similar users, recommend their preferences

    3. Item-Item Collaborative Filtering: Find similar songs, recommend based on user history

    4. Matrix Factorization: Use SVD to discover latent factors in user-song interactions

    5. Clustering-Based: Group users and songs, recommend within clusters

    6. Content-Based: Analyze song metadata to find similar tracks

    Data Understanding & Preprocessing

    Data Scale and Computational Challenges

    The original dataset contains 20 million user-song interactions and 10 million song records. This scale presents significant computational challenges for model training and requires strategic data reduction.

    Filtering Strategy and Rationale

    User Filtering: Retain only users who have listened to at least 90 songs

    • Rationale: Users with very few interactions provide insufficient data for preference modeling

    • Impact: Reduces noise from casual users while maintaining users with established preferences

    Song Filtering: Keep only songs played by at least 120 users

    • Rationale: Songs with few listeners lack sufficient collaborative signal

    • Impact: Focuses on songs with adequate interaction data for pattern recognition

    Play Count Filtering: Consider only interactions with play_count ≤ 5

    • Rationale: Songs with extremely high play counts (outliers) may represent automated behavior or data anomalies

    • Business Logic: Most genuine listening behavior falls within this range

    Final Dataset Characteristics

    After filtering, the dataset contains:

    • 3,155 unique users

    • 563 unique songs

    • 232 unique artists

    Critical Assessment: This aggressive filtering trades dataset size for modeling reliability. While it reduces the recommendation catalog, it ensures higher-quality training data. Production systems would need to balance coverage with prediction accuracy.

    Popularity-Based Recommendations

    Methodology and Use Cases

    Popularity-based systems rank songs by average play counts across all users. This approach serves as both a baseline and a cold-start solution.

    When to Use:

    • New users with no interaction history

    • New songs with insufficient collaborative data

    • Fallback when personalized methods fail

    Implementation Approach

    Ranking Mechanism:

    • Calculate average play count per song

    • Apply minimum interaction threshold (default: 100 interactions)

    • Rank songs by average score

    Threshold Rationale: The minimum interaction requirement filters out songs with insufficient data, preventing statistical noise from dominating recommendations.

    Performance Characteristics

    Strengths:

    • Simple to implement and explain

    • Computationally efficient

    • Always produces recommendations

    • Good for trending content discovery

    Limitations:

    • No personalization

    • Popularity bias favors mainstream content

    • May not reflect individual taste

    • Cold start problem for new songs

    Business Impact: While not personalized, popularity-based recommendations can drive engagement for new users and provide a safety net when other methods fail. However, over-reliance on this approach may lead to filter bubbles and reduced content diversity.

    Collaborative Filtering Methods

    User-User Similarity Approach

    Core Principle: Users with similar listening patterns will enjoy similar songs.

    Methodology:

    • Calculate user similarity using Pearson correlation baseline

    • Find k nearest neighbors for target user

    • Predict ratings based on neighbors' preferences

    • Apply corrected play count ranking

    Performance Metrics Interpretation

    Baseline Model Results:

    • Precision@30: 0.396 (39.6% of recommendations are relevant)

    • Recall@30: 0.70 (70% of relevant songs are recommended)

    • F1-Score: 0.504

    • RMSE: ~1.025

    Optimized Model Results (After Hyperparameter Tuning):

    • Improved F1-Score: 0.517

    • Reduced RMSE: Better prediction accuracy

    Business Interpretation: The high recall indicates the system successfully identifies most songs users will enjoy, while moderate precision suggests some irrelevant recommendations. This trade-off may be acceptable if user engagement increases overall.

    Item-Item Similarity Approach

    Core Principle: Users who liked song A will also like songs similar to song A.

    Advantages over User-User:

    • More stable (songs don't change preferences like users)

    • Better scalability for large song catalogs

    • Easier to precompute similarities

    Optimized Performance:

    • F1-Score: Comparable to user-user approach

    • RMSE: Competitive prediction accuracy

    • Computational Efficiency: Better for real-time serving

    Critical Assessment

    When User-User Works Best:

    • Strong user communities with distinct preferences

    • Sufficient user interaction data

    • Preference patterns change slowly

    When Item-Item Works Best:

    • Large, stable content catalogs

    • Real-time recommendation requirements

    • Users have consistent taste profiles

    Limitations of Both Approaches:

    • Suffer from cold start problems

    • May create filter bubbles

    • Require substantial interaction data

    • Computationally expensive for large-scale systems

    Matrix Factorization Approach

    Theoretical Foundation

    Matrix factorization decomposes the user-item interaction matrix into lower-dimensional user and item factor matrices, capturing latent preferences and song characteristics.

    Mathematical Intuition:

    Predicted Rating = μ + user_bias + item_bias + (user_factors · item_factors)

    Latent Factors Represent:

    • User factors: Musical taste preferences (e.g., genre preference, tempo preference)

    • Item factors: Song characteristics (e.g., danceability, energy level)

    SVD Implementation Results

    Baseline Performance:

    • F1-Score: 0.498

    • RMSE: 1.025

    • Precision@30: ~0.39

    • Recall@30: ~0.67

    Optimized Model (After Grid Search):

    • Parameters: n_epochs=30, lr_all=0.01, reg_all=0.2

    • Slight improvement in F1-Score

    • Better generalization with regularization

    Practical Advantages

    Scalability: Can handle sparse matrices efficiently

    Flexibility: Incorporates user and item biases naturally

    Interpretability: Latent factors can provide insights into user preferences

    Cold Start Mitigation: Can make predictions for users/items with limited data using global statistics

    Limitations and Considerations

    Model Complexity: Requires careful hyperparameter tuning

    Overfitting Risk: Needs regularization with sparse data

    Interpretability Trade-off: Latent factors may not have clear business meaning

    Computational Requirements: Training can be intensive for large datasets

    Real-World Performance: The modest improvement over simpler methods suggests that with this dataset size and sparsity, the additional complexity may not provide significant business value.

    Clustering-Based Systems

    Co-Clustering Methodology

    Co-clustering simultaneously groups users and songs, identifying user segments with similar preferences and song clusters with similar characteristics.

    Approach:

    • Partition users into n_cltr_u clusters

    • Partition songs into n_cltr_i clusters

    • Make predictions based on cluster membership

    • Iteratively optimize cluster assignments

    Performance Analysis

    Baseline Results:

    • F1-Score: 0.472

    • RMSE: Competitive with other methods

    Tuned Model:

    • Optimal Parameters: n_cltr_u=3, n_cltr_i=2, n_epochs=60

    • Performance: Similar to baseline (minimal improvement)

    Business Applications

    Market Segmentation: User clusters can inform marketing strategies

    Content Strategy: Song clusters reveal content gaps and opportunities

    Personalization at Scale: Cluster-based recommendations are computationally efficient

    Limitations

    Cluster Interpretation: User and song clusters may not align with business intuition

    Scalability Concerns: Requires re-clustering as data grows

    Performance Plateau: Limited improvement over simpler methods suggests clustering may not capture the complexity of music preferences effectively

    Cold Start: New users/songs require cluster assignment strategy

    Content-Based Recommendations

    Methodology and Feature Engineering

    Content-based systems recommend songs based on similarity in metadata features rather than user behavior patterns.

    Feature Creation:

    • Combine title, release (album), and artist_name into unified text

    • Apply TF-IDF vectorization with preprocessing

    • Calculate cosine similarity between song feature vectors

    Text Preprocessing Pipeline:

    • Tokenization and lowercase conversion

    • Stop word removal

    • Lemmatization for word normalization

    • TF-IDF feature extraction

    Practical Applications

    Cold Start Solution: Can recommend new songs immediately

    Transparency: Users can understand why songs were recommended

    Diversity Control: Can explicitly optimize for feature diversity

    Cross-Domain: Techniques transfer to other content types

    Implementation Results

    The system successfully identifies similar songs based on metadata. For example, recommending songs similar to "Learn To Fly" produces results with similar artists or album characteristics.

    Limitations and Considerations

    Feature Quality: Limited to available metadata

    • Missing Audio Features: No tempo, energy, or acoustic characteristics

    • Metadata Inconsistencies: Artist name variations, spelling errors

    • Shallow Understanding: Text similarity may not capture musical similarity

    Scalability Issues:

    • Feature Matrix Size: Grows with vocabulary size

    • Computation Complexity: Similarity calculations scale quadratically

    Performance Gaps: Content-based methods typically achieve lower accuracy than collaborative approaches for users with sufficient interaction history.

    Hybrid System Opportunities

    Content-based recommendations work best when combined with collaborative filtering:

    • Use content features to address cold start

    • Apply collaborative filtering for users with interaction history

    • Weight recommendations based on data availability

    Performance Evaluation

    Evaluation Framework

    Metrics Used:

    • Precision@k: Fraction of recommended songs that are relevant

    • Recall@k: Fraction of relevant songs that are recommended

    • F1-Score@k: Harmonic mean of precision and recall

    • RMSE: Root mean squared error for play count prediction

    Relevance Threshold: Songs with predicted play count ≥ 1.5 are considered "recommended"

    Comparative Analysis

    Method Performance Summary:

    Method F1-Score Precision@30 Recall@30 RMSE
    User-User CF (Optimized) 0.517 0.396 0.70 ~1.02
    Item-Item CF (Optimized) ~0.52 ~0.40 ~0.69 ~1.02
    Matrix Factorization 0.498 0.39 0.67 1.025
    Co-Clustering 0.472 - - -

    Business Interpretation

    Best Performing Approach: User-user similarity with optimized hyperparameters

    Key Insights:

    • High Recall (70%): System captures most songs users will enjoy

    • Moderate Precision (40%): 60% of recommendations may not be relevant

    • Business Trade-off: High recall supports discovery, but moderate precision may affect user satisfaction

    Corrected Play Count Ranking

    The tutorial implements a sophisticated ranking adjustment:

    Corrected Score = Predicted Play Count - (1 / √(Song Popularity))

    Purpose: Balances prediction confidence with song popularity to avoid over-recommending mainstream tracks.

    Practical Deployment Considerations

    Resource Requirements:

    • Memory: User-item matrices can be large

    • Computation: Real-time similarity calculations are expensive

    • Storage: Precomputed similarities require significant space

    Recommendation Latency:

    • Batch Processing: Suitable for daily/weekly recommendation updates

    • Real-time Constraints: May require approximation techniques

    Model Refresh Strategy:

    • Data Drift: User preferences evolve over time

    • New Content: Regular retraining needed for new songs/artists

    • Performance Monitoring: Continuous evaluation of recommendation quality

    Limitations and Future Improvements

    Current Limitations:

    • Limited Audio Features: No acoustic analysis of songs

    • Temporal Dynamics: Doesn't account for time-based preferences

    • Diversity Optimization: May create filter bubbles

    • Cross-Domain: No integration with user context (mood, activity)

    Potential Enhancements:

    • Deep Learning: Neural collaborative filtering

    • Multi-Modal: Combine audio features with interaction data

    • Contextual: Time-aware and situation-aware recommendations

    • Explainability: User-facing recommendation explanations

    Data Preprocessing & Filtering

    User Interaction Threshold Implementation

    # Get the column containing the users
users = df.user_id

# Create a dictionary that maps users to their song count
playing_count = dict()

for user in users:
    if user in playing_count:
        playing_count[user] += 1
    else:
        playing_count[user] = 1

# Filter users with less than 90 songs
SONG_COUNT_CUTOFF = 90
remove_users = []

for user, num_songs in playing_count.items():
    if num_songs < SONG_COUNT_CUTOFF:
        remove_users.append(user)

df = df.loc[~df.user_id.isin(remove_users)]

    Purpose: Removes users with insufficient interaction history to ensure reliable preference modeling.

    Flow: - Counts songs per user using dictionary - Identifies users below threshold - Filters DataFrame to exclude low-interaction users

    Impact: Trades dataset size for model reliability. Removes noise from casual users but may exclude legitimate users with limited history.

    Mathematical Foundation: Collaborative filtering requires sufficient user-item interactions to identify meaningful patterns. Users with few interactions provide weak signal for similarity calculations.

    Song Popularity Threshold Implementation

    # Get the column containing the songs
songs = df.song_id

# Create a dictionary that maps songs to their listener count
playing_count = dict()

for song in songs:
    if song in playing_count:
        playing_count[song] += 1
    else:
        playing_count[song] = 1

# Filter songs with less than 120 listeners
LISTENER_COUNT_CUTOFF = 120
remove_songs = []

for song, num_users in playing_count.items():
    if num_users < LISTENER_COUNT_CUTOFF:
        remove_songs.append(song)

df_final = df.loc[~df.song_id.isin(remove_songs)]

    Purpose: Removes songs with insufficient listener data to ensure collaborative signals exist.

    Flow: - Counts listeners per song - Identifies songs below threshold - Filters DataFrame to exclude unpopular songs

    Impact: Ensures songs have adequate interaction data for collaborative filtering but reduces catalog coverage.

    # Keep only records with play_count <= 5
df_final = df_final[df_final.play_count <= 5]

    Impact: Reduces data skew and focuses on typical user behavior patterns. May exclude legitimate heavy listening.

    Statistical Rationale: The original analysis showed 90% of interactions have play_count ≤ 5, making this a reasonable threshold for normal behavior.

    Precision and Recall Evaluation Function

    def precision_recall_at_k(model, k=30, threshold=1.5):
    """Return precision and recall at k metrics for each user"""

    # Map predictions to each user
    user_est_true = defaultdict(list)

    # Make predictions on test data
    predictions = model.test(testset)

    for uid, _, true_r, est, _ in predictions:
        user_est_true[uid].append((est, true_r))

    precisions = dict()
    recalls = dict()

    for uid, playing_count in user_est_true.items():
        # Sort by estimated value (descending)
        playing_count.sort(key=lambda x: x[0], reverse=True)

        # Count relevant items (true rating >= threshold)
        n_rel = sum((true_r >= threshold) for (_, true_r) in playing_count)

        # Count recommended items in top k (estimated >= threshold)
        n_rec_k = sum((est >= threshold) for (est, _) in playing_count[:k])

        # Count relevant AND recommended items in top k
        n_rel_and_rec_k = sum(((true_r >= threshold) and (est >= threshold))
                              for (est, true_r) in playing_count[:k])

        # Calculate precision@k
        precisions[uid] = n_rel_and_rec_k / n_rec_k if n_rec_k != 0 else 0

        # Calculate recall@k  
        recalls[uid] = n_rel_and_rec_k / n_rel if n_rel != 0 else 0

    # Calculate overall metrics
    precision = round((sum(prec for prec in precisions.values()) / len(precisions)), 3)
    recall = round((sum(rec for rec in recalls.values()) / len(recalls)), 3)

    accuracy.rmse(predictions)
    print('Precision: ', precision)
    print('Recall: ', recall) 
    print('F_1 score: ', round((2*precision*recall)/(precision+recall), 3))

    Purpose: Implements standard recommendation evaluation metrics with configurable parameters.

    Flow: - Collects predictions by user - Sorts predictions by confidence - Counts relevant, recommended, and relevant-recommended items - Calculates precision, recall, and F1-score per user - Averages across all users

    Impact: Provides standardized evaluation framework for comparing different algorithms.

    Mathematical Foundation: - Precision@k = |relevant ∩ recommended|@k / |recommended|@k - Recall@k = |relevant ∩ recommended|@k / |relevant| - F1-score = 2 × (precision × recall) / (precision + recall)

def tokenize(text):
    # Remove non-alphabetic characters and convert to lowercase

    def get_recommendations(data, user_id, top_n, algo):
    recommendations = []

    # Create user-item interaction matrix
    user_item_interactions_matrix = data.pivot(index='user_id', 
                                               columns='song_id', 
                                               values='play_count')

    # Find songs not yet interacted with by the user
    non_interacted_songs = user_item_interactions_matrix.loc[user_id][
        user_item_interactions_matrix.loc[user_id].isnull()].index.tolist()

    # Predict play_count for each non-interacted song
    for item_id in non_interacted_songs:
        est = algo.predict(user_id, item_id).est
        recommendations.append((item_id, est))

    # Sort by predicted play_count (descending)
    recommendations.sort(key=lambda x: x[1], reverse=True)

    return recommendations[:top_n]

    Purpose: Generates top-N recommendations for any user using any trained algorithm.

    Flow: - Creates user-item matrix to identify missing interactions - Predicts ratings for all unobserved items - Sorts predictions and returns top-N

    Impact: Provides unified interface for generating recommendations across different algorithms.

    Design Features: - Algorithm agnostic: Works with any Surprise algorithm - Efficient filtering: Only predicts for unobserved items - Scalable: Returns configurable number of recommendations

    Corrected Play Count Ranking Function

    def ranking_songs(recommendations, playing_count):
    # Sort songs by play frequency
    ranked_songs = playing_count.loc[[items[0] for items in recommendations]].sort_values(
        'play_freq', ascending=False)[['play_freq']].reset_index()

    # Merge with predicted play_counts
    ranked_songs = ranked_songs.merge(
        pd.DataFrame(recommendations, columns=['song_id', 'predicted_play_count']), 
        on='song_id', how='inner')

    # Calculate corrected play_count (popularity adjustment)
    ranked_songs['corrected_play_count'] = (ranked_songs['predicted_play_count'] - 
                                            1 / np.sqrt(ranked_songs['play_freq']))

    # Sort by corrected play_count
    ranked_songs = ranked_songs.sort_values('corrected_play_count', ascending=False)

    return ranked_songs

    Purpose: Adjusts recommendation scores to balance prediction confidence with song popularity.

    Flow: - Retrieves popularity data for recommended songs - Merges with prediction scores - Applies popularity penalty (1/√frequency) - Re-ranks based on corrected scores

    Impact: Prevents over-recommendation of extremely popular songs while maintaining prediction quality.

    Mathematical Rationale: The correction term 1/√(play_freq) penalizes popular songs proportionally to the square root of their frequency, preventing popularity bias while maintaining reasonable penalties.
